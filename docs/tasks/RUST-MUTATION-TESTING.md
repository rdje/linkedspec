# RUST-MUTATION-TESTING: Evidence-Based Rust Test Strength

- Last updated: `2026-07-15`
- Owner: repo-local workflow

## Goal

Use `cargo-mutants` to find Rust semantic changes that the existing tests fail to detect, then convert meaningful
survivors into focused regression proof while keeping the workflow bounded, reproducible, and useful.

## Non-Goals

- Do not run mutation execution—full, diff-scoped, or file-scoped—on every commit, in pre-commit hooks, or in
  ordinary local CI.
- Do not optimize for a context-free mutation-score percentage.
- Do not treat every survivor as a defect, or hide meaningful survivors behind broad exclusions.
- Do not mutate generated Unicode tables; verify their generator, exact bytes, and behavior contracts instead.
- Do not run a full campaign before repo-owned scope, resource, output, and classification policy exists.
- Do not make Rust-only mutation tooling a semantic backend-parity requirement.

## Invariants

1. Ordinary Rust tests must pass before any mutation result is interpreted.
2. Hand-written parser, validation, compiler, ActionIR, runtime, helper, loader, staged, diagnostic, trace, and
   source-emitter semantics are in scope.
3. `rust/linkedspec-runtime/src/unicode_case_mapping.rs` is excluded because it is mechanically generated and
   byte-regenerated by `tools/check_unicode_case_contract.py`; the generator/contract/runtime proof remains its
   authority.
4. Thin adapters are not excluded categorically. They remain in scope when they own observable CLI, error,
   identity, trace, or serialization behavior.
5. Every survivor is classified as test gap, equivalent/redundant behavior, unreachable/dead code, deliberately
   unspecified behavior, or tool limitation. Test gaps get tests; exclusions require narrow durable rationale.
6. Timeout and unviable outcomes are separate from caught and survived outcomes; none silently count as success.
7. Mutation campaigns are never per-commit gates. Explicit on-demand investigations may use diff/file scope;
   broader campaigns are resource-guarded, sharded, and reserved for meaningful milestones, releases, or admission.
8. Mutation output and scratch directories are rebuildable artifacts outside tracked source, with deterministic
   cleanup and no dependency on hosted CI.
9. Tool version, command, config fingerprint, baseline duration, selected scope, counts, and outcome classifications
   accompany every durable result.
10. A score may summarize a fixed comparable campaign, but survivor dispositions and newly strengthened contracts
    are the signoff evidence.

## Measured Planning Baseline

On 2026-07-15, installed `cargo-mutants 27.0.0` listed 3,333 candidate mutations across 19 production files without
executing mutants: 1,217 in `linkedspec-core` and 2,116 in `linkedspec-runtime`. The largest files were
`engine.rs` (1,343), `expr.rs` (522), and `parser.rs` (320). Genres were 1,471 binary-operator, 1,112 function-value,
457 match-arm, 192 unary-operator, 100 match-guard, and one struct-field mutation. This scale rules out an
unsharded every-commit full campaign.

## Decisions

- Adopt `cargo-mutants` as a targeted Rust test-strength tool.
- Do not execute any mutation campaign on per-commit, pre-commit, or ordinary-local-CI paths.
- Use diff/file scope only for explicit investigations and sharding for later milestone/release breadth.
- Exclude the generated Unicode table; do not broadly exclude adapters or large semantic files.
- Judge the program by survivor disposition and improved contracts, not a raw percentage alone.
